HTTP/2 e HTTP/3 (QUIC)

O HTTP/1.1 é como uma fila única de banco com um guichê só: cada pedido espera o anterior terminar (e o navegador abria várias conexões só para enganar). O HTTP/2 (2015) trouxe vários guichês na mesma conexão (multiplexing). O HTTP/3 (2022) foi além: trocou o transporte TCP pelo QUIC, que roda sobre UDP — menos latência e sem o bloqueio de fila do TCP.

Você vai aprender
  • Os problemas do HTTP/1.1: uma conexão por recurso, head-of-line blocking, headers repetidos;
  • O que mudou no HTTP/2: binário, multiplexing, HPACK, server push, sempre sobre TLS na prática;
  • O que mudou no HTTP/3: QUIC sobre UDP, 0-RTT, sem head-of-line blocking de transporte, migração de rede;
  • Tabela comparativa HTTP/1.1 × HTTP/2 × HTTP/3;
  • Ver as versões diferentes com curl -i no simulador.

HTTP/1.1: o gargalo da fila única

Numa página moderna há dezenas de recursos (HTML, vários CSS, vários JS, imagens, fontes). No HTTP/1.1 cada conexão trafega um pedido por vez, e as respostas chegam na ordem — se o primeiro arquivo for lento, todos os outros esperam (isso é o head-of-line blocking). Por isso os navegadores abriam até 6 conexões paralelas para a mesma origem, e os sites "apelavam" para juntar arquivos (sprites, CSS inline) — gambiarras que o HTTP/2 eliminou.

HTTP/2: vários pedidos na mesma conexão

  • Binário: as mensagens viraram frames binários (mais rápidos de parsear que texto puro);
  • Multiplexing: vários pedidos e respostas ao mesmo tempo, numa única conexão TCP, cada um com seu stream ID — adeus fila única;
  • HPACK: compressão dos headers (eles se repetem muito: User-Agent, Accept, cookies…);
  • Server push: o servidor pode mandar o CSS/JS antes mesmo de você pedir (hoje pouco usado, mas existe);
  • Sempre sobre TLS na prática: todos os navegadores só falam HTTP/2 em HTTPS (h2).

Resultado: a página carrega com uma conexão só, sem gambiarra de juntar arquivos, e sem esperar o recurso lento travar os outros.

HTTP/3: QUIC sobre UDP

O HTTP/2 ainda sofria com o TCP: se um pacote TCP se perde, todos os streams daquela conexão param esperando a retransmissão (head-of-line blocking do transporte). O HTTP/3 risca o TCP do mapa: o transporte passa a ser o QUIC, um protocolo novo que roda sobre UDP e já vem com criptografia (TLS 1.3) de fábrica:

  • Streams independentes: perde um pacote? só aquele stream espera; os outros continuam;
  • 0-RTT / 1-RTT: na reconexão, o handshake é quase instantâneo (com o servidor já conhecido, manda dados junto);
  • Migração de rede: trocou de Wi-Fi para 4G no meio do download? a conexão continua (o QUIC usa um connection ID, não o IP+porta);
  • QPACK: a evolución do HPACK para o QUIC.

Vendo as versões no simulador

O simulador imita exatamente essa diferença: HTTP (porta 80) responde HTTP/1.1; HTTPS (porta 443) responde HTTP/2 — como na vida real, onde o navegador só negocia HTTP/2 sobre TLS:

Missão 1: rode curl -i http://exemplo.com — repare no HTTP/1.1 200 OK (porta 80, sem criptografia).

Missão 2: rode curl -i https://exemplo.com — repare no HTTP/2 200 (porta 443, TLS + multiplexing). Na web moderna, HTTPS = HTTP/2 (ou HTTP/3).

HTTP/2 não é bala de prata

Multiplexing sobre uma única conexão pode piorar em redes com muita perda de pacotes (um pacote perdido trava todos os streams do TCP). É por isso que o HTTP/3 existe. E lembre: HTTP/2/3 não substituem o cache da CDN nem a compressão — as três coisas trabalham juntas.

Resumo

  • HTTP/1.1: uma fila por conexão; o navegador abria várias conexões para contornar.
  • HTTP/2: binário + multiplexing (vários pedidos numa conexão TCP) + HPACK + TLS obrigatório na prática.
  • HTTP/3: HTTP sobre QUIC/UDP, com TLS 1.3 embutido, streams independentes, 0-RTT e Continuidade ao trocar de rede.
  • No simulador: curl -i http://… → HTTP/1.1 200 OK; curl -i https://… → HTTP/2 200.
