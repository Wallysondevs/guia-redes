Segurança web: OWASP Top 10

Um prédio pode ter portaria boa e mesmo assim ser invadido por uma janela esquecida no terceiro andar. Em aplicações web acontece o mesmo: não adianta o TLS e o firewall se o código tem uma porta dos fundos aberta. A OWASP Top 10 é a lista, mantida pela comunidade OWASP, das 10 falhas de segurança mais comuns e críticas em aplicações web — a "lista de janelas esquecidas" que todo dev precisa fechar.

Você vai aprender
  • As 10 categorias da OWASP Top 10 (edição 2021) e o que significa cada uma;
  • Exemplos concretos: SQL injection, XSS, CSRF, SSRF, senhas fracas;
  • A defesa prática para cada uma (validar, parametrizar, CSP, HTTPS, atualizações);
  • A mentalidade: nunca confie no dado que vem do usuário;
  • Ver uma resposta de erro bem comportada (404 genérico) com curl -i.

As 10 falhas (OWASP Top 10 — 2021)

#NomeEm uma fraseDefesa principal
A01Controle de acesso quebradoUsuário comum consegue acessar página/dado de outro usuário (mudar só o ID na URL).Verificar permissão no servidor, em TODAS as rotas (não só esconder o link).
A02Falhas criptográficasDados sensíveis (senhas, cartões) guardados ou transmitidos sem criptografia.HTTPS em tudo, hash de senha forte (bcrypt/argon2), criptografar dados em repouso.
A03InjeçãoCódigo malicioso entrou pelo campo de busca/login (SQL injection, XSS, comando no SO).Consultas parametrizadas, validar/escapar entrada, CSP contra XSS.
A04Design inseguroA arquitetura já nasce errada (ex.: redefinir senha mandando a nova por e-mail em texto claro).Modelagem de ameaças (threat modeling) antes de codar.
A05Má configuração de segurançaServidor com página de exemplo, listagem de diretório ligada, erro detalhado em produção, padrão de fábrica.Hardening, desativar o desnecessário, erros genéricos para o usuário.
A06Componentes vulneráveisBiblioteca/framework desatualizado com falha pública conhecida.Atualizar sempre, npm audit/dependabot, remover o que não usa.
A07Falhas de autenticaçãoSenha fraca, força bruta permitida, token de sessão previsível, "lembrar de mim" mal feito.Senha forte + 2FA, limitar tentativas, sessão aleatória e expirável.
A08Falhas de integridadeAtualização/CI-CD sem assinatura; plugin baixado de fonte duvidosa.Assinar releases, verificar integridade (hashes/assinaturas), pipeline seguro.
A09Falhas de log e monitoramentoAtaque acontece e ninguém percebe (sem log ou log sem nada útil).Logar eventos de segurança, alertar, monitorar (e não logar senha!).
A10SSRF (Server-Side Request Forgery)O servidor faz requisição para um endereço que o atacante escolheu (ex.: http://169.254.169.254, os metadados da nuvem).Validar/bloquear destinos, lista de IPs permitidos, segmento de rede isolado.

Os três mais famosos em detalhe

A03 — Injeção de SQL (SQLi)

Se o site monta a consulta colando o que o usuário digitou, o atacante vira o comando. Clássico: no campo de login, digitar ' OR '1'='1 — a consulta vira SELECT … WHERE user='' OR '1'='1', que é sempre verdade, e o atacante entra sem senha. Defesa: consultas parametrizadas (prepared statements) — o banco trata a entrada sempre como dado, nunca como código.

A03 — XSS (Cross-Site Scripting)

O atacante injeta um <script> num campo (ex.: comentário) e ele roda no navegador de quem lê a página — roubando cookie de sessão. Defesa: escapar a saída no HTML, usar Content-Security-Policy (CSP) para limitar de onde scripts podem vir, e marcar cookies com HttpOnly (JavaScript não lê).

CSRF (dentro de A01/A04)

Você está logado no banco; um site malicioso faz seu navegador disparar um pedido para o banco (transferir dinheiro) sem você saber — o navegador manda o cookie sozinho. Defesa: token CSRF único por sessão nos formulários e ações, e verificar o header Origin/Referer.

A mentalidade que evita quase tudo

  • Nunca confie no cliente: valide e saneie TUDO no servidor (campos, headers, cookies, arquivos) — o navegador pode ser alterado, o curl manda o que quiser;
  • Mínimo privilégio: o banco de dados da aplicação não deve ser root; cada serviço, sua permissão;
  • Erros genéricos para o usuário: um erro de banco não pode mostrar a consulta SQL nem o caminho do arquivo (isso ajuda o atacante);
  • Mantenha tudo atualizado e remova páginas de teste/padrão;
  • Teste você mesmo: aprenda no seu próprio lab (OWASP Juice Shop, DVWA) e faça pentest com autorização.

Missão: rode curl -i http://exemplo.com/nao-existe e veja o HTTP/1.1 404 Not Found com corpo genérico — assim é um erro seguro: não vaza caminho de arquivo, consulta SQL nem versão interna. Compare com curl -i https://api.exemplo.com/usuarios/999 (o 404 da API também é genérico: {"erro":"usuário não encontrado"}).

Segurança é processo, não ferramenta

Não existe "site 100% seguro". Existe: código revisado, dependências atualizadas, HTTPS com HSTS, firewall, logs, backup testado e um plano para quando (não se) algo der errado. A OWASP Top 10 muda a cada poucos anos — acompanhe em owasp.org.

Resumo

  • OWASP Top 10 (2021): A01 acesso quebrado, A02 criptografia, A03 injeção (SQLi/XSS), A04 design inseguro, A05 má configuração, A06 componentes vulneráveis, A07 autenticação, A08 integridade, A09 logs, A10 SSRF.
  • Defesas recorrentes: validar tudo no servidor, consultas parametrizadas, CSP + cookies HttpOnly, HTTPS+HSTS, 2FA, atualizações constantes, erros genéricos, logs.
  • Nunca confie no que vem do usuário — e pratique em labs próprios (Juice Shop, DVWA, HackTheBox).
