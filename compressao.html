Compressão: gzip e Brotli

Uma página web é, no fundo, texto: HTML, CSS, JavaScript, JSON — e texto se comprime muito bem, como uma carta dobrada a vácuo antes de ir para o correio (mesma carta, pacote bem menor). Se o seu HTML de 100 KB sai com 25 KB, a página carrega 4 vezes mais rápido em conexões lentas. Essa é a compressão de conteúdo: gzip (o clássico) e Brotli (o moderno).

Você vai aprender
  • Como funciona a negociação: Accept-Encoding no pedido → Content-Encoding na resposta;
  • Quanto dá para economizar: texto comprime 70–90%;
  • Tabela comparativa: sem compressão × gzip × Brotli;
  • O que NÃO se comprime de novo (imagens, vídeos, ZIP…);
  • Configuração no nginx e o risco histórico BREACH.

A negociação pelo header

O cliente (navegador, curl) diz o que aceita no pedido e o servidor escolhe o melhor formato que consegue entregar:

GET / HTTP/1.1
Host: exemplo.com
Accept-Encoding: gzip, deflate, br      ← "aceito gzip ou Brotli"

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Encoding: gzip                  ← "mandei em gzip"
Content-Length: 1256                    ← tamanho DEPOIS de comprimir (o original tinha mais)
Vary: Accept-Encoding                   ← "essa resposta varia conforme o Accept-Encoding"
Accept-Encoding
Enviado pelo cliente com a lista de algoritmos que ele entende: gzip, deflate, br.
Content-Encoding
A resposta diz qual foi usado: gzip ou br (Brotli).
Content-Length
Depois de comprimido — é por isso que a página "fica menor" na rede.
Vary: Accept-Encoding
Avisa caches/CDNs que a mesma URL pode ter versões diferentes (comprimida ou não) conforme o pedido — importante para a CDN não servir a versão errada.

Regra prática: texto comprime muito (HTML/CSS/JS/JSON/SVG), arquivos já comprimidos não ganham nada (JPEG, PNG, MP4, ZIP, PDF…).

Configurando no nginx (e no proxy reverso)

# /etc/nginx/nginx.conf
http {
    gzip on;
    gzip_types text/html text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1000;          # não comprima arquivos minúsculos (não vale a pena)
    gzip_comp_level 5;             # nível 1–9 (5 é o meio-termo bom)

    brotli on;                     # precisa do módulo ngx_brotli
    brotli_types text/html text/css application/javascript application/json image/svg+xml;
    brotli_comp_level 6;
}

Em curl, dá para ver a diferença pedindo o conteúdo comprimido: curl -i -H "Accept-Encoding: gzip" http://exemplo.com — o servidor responde com Content-Encoding: gzip e um Content-Length bem menor.

Missão: rode curl -i http://exemplo.com e veja o header Content-Length: 1256. Na vida real, com gzip ligado, esse número seria bem menor (o HTML original é maior). Compare também curl -i https://exemplo.com e wget exemplo.com (que mostra o tamanho salvo).

Dois cuidados importantes

(1) Não comprima duas vezes: imagens, vídeos e ZIP já são comprimidos — passar gzip em cima só gasta CPU e pode até aumentar o tamanho. Liste só texto nos *_types. (2) BREACH: antigamente, comprimir uma página que mistura conteúdo público com um segredo (ex.: token CSRF) permitia adivinhar o segredo pelo tamanho da resposta comprimida. Hoje isso está mitigado (TLS moderno, e a dica de não comprimir respostas com dados sensíveis embutidos) — mas lembre que compressão + segredo na mesma resposta é perigoso.

Resumo

  • Compressão de conteúdo = mandar o texto "dobrado a vácuo": Accept-Encoding: gzip, br → resposta com Content-Encoding e Content-Length menor.
  • Texto (HTML/CSS/JS/JSON) comprime 70–90%; gzip é universal, Brotli é ~20% menor e só funciona sobre HTTPS.
  • No nginx: gzip on + brotli on com a lista de *_types só de texto e gzip_min_length.
  • Nunca comprima de novo arquivos já comprimidos (imagem/vídeo/zip) e cuidado com BREACH (segredo + compressão na mesma resposta).
  • A Vary: Accept-Encoding garante que a CDN guarde versões separadas por formato.
