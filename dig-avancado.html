dig avançado — além do básico

Na aula dig/nslookup você fez a consulta simples. Agora as opções que transformam o dig numa lupa de DNS: +short (só a resposta), +trace (o caminho inteiro), o tipo específico (dig HOST MX) e trocar de servidor com @.

Sintaxe geral 
dig [@servidor] HOST [TIPO] [+short|+trace]
Você vai aprender
  • +short — só o valor da resposta (perfeito para scripts).
  • +trace — a jornada raiz → TLD → autoritativo.
  • dig HOST TIPO — perguntar um tipo específico (A, MX, TXT…).
  • dig @8.8.8.8 HOST — perguntar para outro resolver.
  • Ler as seções da resposta e interpretar NXDOMAIN.

+short: só a resposta

Com +short, o dig imprime somente o valor — ideal para guardar num script:

$ dig exemplo.com +short
93.184.216.34
$ dig google.com +short
142.250.72.142
$ dig exemplo.com +short | head -1     « num servidor real, pega só a 1ª linha

Missão: pegue só o IP, sem o resto da resposta: dig exemplo.com +short

+trace: a jornada completa

O +trace começa na raiz e vai perguntando andar por andar até chegar na resposta final (aula DNS a fundo):

$ dig exemplo.com +trace
; <<>> DiG 9.18 <<>> +trace exemplo.com
;; global options: +cmd
.                       518400  IN  NS  a.root-servers.net.    « a raiz: "quem cuida de .com?"
;; Received 239 bytes from 192.168.1.1#53(192.168.1.1) in 4 ms

com.                    172800  IN  NS  a.gtld-servers.net.     « o TLD .com: "quem cuida de exemplo.com?"

exemplo.com.            86400   IN  NS  ns1.exemplo.com.       « o autoritativo: tem a resposta

exemplo.com.            3600    IN  A   93.184.216.34         « a resposta final
;; Query time: 38 msec
;; SERVER: 8.8.8.8#53(8.8.8.8)

Missão: siga o rastro até o TLD .com: dig exemplo.com +trace — ache gtld-servers

Trocando de servidor: @servidor

Com @ você escolhe qual resolver faz a pergunta — útil para comparar respostas:

dig @8.8.8.8 exemplo.com        « pergunta direto no DNS do Google
dig @192.168.1.1 exemplo.com    « pergunta no roteador (resolver local)

Se o roteador devolver um IP diferente do 8.8.8.8, o cache dele está sujo ou há algum redirecionamento esquisito na rede.

Lendo as seções da resposta

SeçãoO que mostra
;; HEADERO status da consulta: NOERROR (deu certo) ou NXDOMAIN (domínio não existe).
;; QUESTION SECTIONO que foi perguntado (nome + tipo).
;; ANSWER SECTIONA resposta: nome, TTL (segundos), tipo e valor.
;; SERVER / Query timeQual resolver respondeu e em quanto tempo.
$ dig naoexiste.com
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 7312
;; QUESTION SECTION:
;naoexiste.com.         IN      A

;; ANSWER SECTION:

;; Query time: 12 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)

Missão: provoque um NXDOMAIN perguntando um domínio que não existe: dig naoexiste.com

Missão: compare com o nslookup (saída mais simples, mesma resposta): nslookup exemplo.com

Dois erros clássicos de DNS:
  • NXDOMAIN = o domínio não existe (erro de digitação ou registro nunca feito).
  • connection timed out; no servers could be reached = o servidor DNS não respondeu (rede caída ou resolver fora do ar).

Para diagnosticar, compare dig exemplo.com (resolver local) com dig @8.8.8.8 exemplo.com (outro resolver).

O que o dig +short faz?

Resumo

  • Sintaxe: dig [@servidor] HOST [TIPO] [+short|+trace].
  • +short = só o valor; +trace = raiz → TLD → autoritativo; TIPO = A, MX, TXT…; @8.8.8.8 = trocar de resolver.
  • Leia o HEADER: NOERROR = ok; NXDOMAIN = domínio não existe; timeout = resolver não respondeu.
