WebSockets: conversa contínua

O HTTP é como telefonar: você liga, faz um pedido, recebe a resposta e desliga. E se você precisasse de atualizações o tempo todo — um chat, o placar de um jogo, a cotação da bolsa? Ligar e desligar a cada 2 segundos seria um desastre. O WebSocket é a linha telefônica que fica aberta: depois de aberta, os dois lados falam quando quiserem, nos dois sentidos, na mesma conexão.

Você vai aprender
  • A diferença entre HTTP (requisição/resposta) e WebSocket (full-duplex contínuo);
  • Como a conexão começa: o upgrade do HTTP com 101 Switching Protocols;
  • ws:// × wss:// (o "s" é o TLS — obrigatório na prática);
  • Casos de uso reais: chat, notificações, jogos, edição colaborativa, IoT;
  • Os riscos: CSWSH, validar a origem, e o que acontece quando a conexão cai.

Do HTTP para o WebSocket: o handshake de upgrade

O WebSocket começa como um pedido HTTP normal, com um detalhe no header: Upgrade: websocket. Se o servidor aceitar, ele responde 101 Switching Protocols e a partir daí a conexão vira um túnel aberto nos dois sentidos — não é mais HTTP:

GET /chat HTTP/1.1
Host: exemplo.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Depois do 101, as duas pontas trocam frames leves (mínimo de 2 bytes de header) a qualquer momento, para qualquer lado — sem precisar de novo handshake TCP/TLS. Em JavaScript no navegador é um new WebSocket("wss://exemplo.com/chat").

Por que não usar HTTP puro para isso?

Dá para simular tempo real com HTTP: o cliente fica perguntando "tem novedade?" a cada segundo (polling) — gasta banda e bateria, e a atualização chega atrasada. Ou o servidor segura a resposta até ter novedade (long polling) — funciona, mas cada pedido ocupa uma conexão e um processo no servidor. O WebSocket resolve limpamente: uma conexão, mensagens instantâneas nos dois lados. Por isso chat (WhatsApp Web), jogos online e dashboards em tempo real usam WebSocket (ou o primo moderno dele, Server-Sent Events para fluxo servidor→cliente só).

Cuidados de segurança

  • Use sempre wss:// (WebSocket sobre TLS), como o https:// — ws:// vai em texto claro;
  • Valide o header Origin no servidor: senão outro site pode abrir um WebSocket no navegador do usuário e atacar sua aplicação (CSWSH — Cross-Site WebSocket Hijacking), usando a sessão logada da vítima;
  • Autentique a conexão (token na URL ou no primeiro frame) — o WebSocket em si não tem login;
  • Trate a queda da conexão: reconectar com backoff, avisar o usuário, não perder mensagens (a conexão cai fácil em celular trocando de Wi-Fi para 4G);
  • O WebSocket passa pelo proxy reverso e pela CDN — eles precisam estar configurados para segurar a conexão aberta (timeout longo).

Missão: rode nc -zv exemplo.com 443 e veja succeeded! — é uma conexão TCP que fica aberta com o servidor, a mesma ideia do WebSocket (que, por baixo, também é TCP na porta 443 com wss). rode também ss -tlnp para ver as portas locais escutando.

WebSocket não é mágica infinita

Cada conexão aberta consome memória no servidor — um servidor aguenta dezenas de milhares de WebSockets, não milhões (diferente de pedidos HTTP curtos). Para escala gigante usam-se soluções como Socket.IO, SSE, ou serviços gerenciados. E o WebSocket não substitui o HTTP: páginas e APIs continuam em HTTP; o WebSocket entra só onde o tempo real importa.

Resumo

  • HTTP = liga, pede, desliga. WebSocket = conexão aberta, full-duplex, para mensagens em tempo real nos dois lados.
  • Começa com um pedido HTTP com Upgrade: websocket; o servidor responde 101 Switching Protocols e vira túnel.
  • Use wss:// (TLS), valide Origin, autentique a conexão e trate a reconexão.
  • Casos de uso: chat, notificações, jogos, cotações, edição colaborativa. Complementa o HTTP — não substitui.
