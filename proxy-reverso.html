Proxy reverso (nginx)

Num prédio comercial, você não bate na porta de cada sala: você fala com a recepcionista, e ela encaminha para a sala certa. Na internet existe o mesmo papel: o proxy. Existe o proxy "direto" (do lado do cliente) e o proxy reverso (do lado do servidor) — e é este último, geralmente um nginx, que faz a mágica de muitos sites.

Você vai aprender
  • A diferença entre proxy direto (cliente) e proxy reverso (servidor);
  • Configurar o nginx como proxy reverso com proxy_pass;
  • Os headers X-Real-IP, X-Forwarded-For e X-Forwarded-Proto;
  • Para que serve na prática: TLS, cache, load balance e esconder os servidores internos;
  • Ver a resposta chegando "pelo proxy" com curl -i.

Proxy direto × proxy reverso

A analogia da recepcionista funciona pros dois lados:

Proxy reverso na prática (nginx)

A Ana tem uma aplicação rodando só na máquina dela, na porta 3000 (http://127.0.0.1:3000), e não quer expor isso direto. Ela coloca um nginx na frente, escutando na 443, que recebe o pedido HTTPS, descriptografa e encaminha para a aplicação:

# /etc/nginx/sites-enabled/meusite
server {
    listen 443 ssl;
    server_name exemplo.com;

    ssl_certificate     /etc/letsencrypt/live/exemplo.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/exemplo.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;          # encaminha para a app
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;              # IP de quem pediu de verdade
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;           # http ou https
    }
}
proxy_pass
O endereço interno para onde o nginx encaminha o pedido (a "sala" atrás da recepção).
X-Real-IP / X-Forwarded-For
Como o servidor interno descobre o IP real do cliente — sem isso, ele só veria o IP do proxy (127.0.0.1), e os logs ficariam inúteis.
X-Forwarded-Proto
Informa se o pedido original veio por HTTP ou HTTPS — o app precisa saber para montar URLs corretas.
listen 443 ssl + certificados
O proxy reverso também faz o TLS (o "certificado no cadeado" fica nele, não na aplicação) — chama-se TLS termination.

Para que serve um proxy reverso

  • Esconder os servidores internos: o mundo vê só o proxy; a aplicação na porta 3000 não precisa ser alcançável de fora (o firewall bloqueia — aula firewall);
  • TLS/HTTPS num lugar só, com certificados fáceis de renovar (Let's Encrypt);
  • Cache: páginas estáticas servidas pelo proxy sem bater na aplicação;
  • Load balancing: o proxy distribui os pedidos entre vários servidores (próxima aula, load balancer);
  • Compressão (aula compressão) e WAF (firewall de aplicação).

Missão: rode curl -i http://exemplo.com. A resposta HTTP/1.1 200 OK com Server: nginx/1.25.3 veio do proxy, no lugar do servidor interno — é exatamente o que um proxy reverso faz. Compare com curl -i https://exemplo.com (que mostra HTTP/2 200 e HSTS, o TLS terminando no proxy).

Detalhe importante: o Host

Muitos servidores hospedam vários sites na mesma máquina (virtual hosts). O proxy reverso precisa mandar o header Host original (proxy_set_header Host $host;) — senão o servidor de trás não sabe qual site você pediu e responde com o padrão (ou erro). Esquecer esse header é um dos erros mais comuns de configuração de nginx.

Resumo

  • Proxy direto = intermediário do lado do cliente; proxy reverso = intermediário do lado do servidor (quem vê de fora não sabe que existe).
  • O nginx como proxy reverso: proxy_pass para a app interna + headers X-Real-IP, X-Forwarded-For, X-Forwarded-Proto e Host.
  • Benefícios: esconder servidores, TLS centralizado, cache, load balance e WAF na borda.
  • O curl -i mostra o Server: nginx — a resposta veio do proxy, não da aplicação.
