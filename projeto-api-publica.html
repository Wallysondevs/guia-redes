Projeto 2 — API pública com curl + dig

No projeto 1 o servidor estava na sua própria máquina. Agora a Ana vai falar com um servidor do outro lado do mundo: uma API pública. Pense numa API como num balcão de pedidos: você não entra na cozinha — manda o pedido por uma URL (com um método, tipo GET ou POST) e recebe uma resposta com status e um JSON. Primeiro a gente descobre o endereço (DNS), depois faz o pedido (HTTP).

Você vai aprender
  • O fluxo completo para chamar uma API: dig (qual o IP?) → curl (qual a resposta?).
  • dig api.exemplo.com +short — só o IP, sem enfeite.
  • curl -i https://api.exemplo.com/usuarios — status HTTP/2 200 + JSON no corpo.
  • Um 404 real: curl -i https://api.exemplo.com/usuarios/999.
  • Enviar dados com curl -X POST -d '{...}' e espiar a conversa com curl -v.

Passo 1 — descobrir o IP (DNS)

Antes de bater na porta, o computador precisa traduzir o nome api.exemplo.com num IP. É o trabalho do DNS — a agenda telefônica da internet. O dig ... +short responde só com o IP, ideal para scripts:

$ dig api.exemplo.com +short
93.184.216.35

Missão: rode dig api.exemplo.com +short e anote o IP da API.

Passo 2 — chamar a API (GET) e ler o status

Agora o pedido: GET /usuarios na porta 443 (HTTPS). Com -i, o curl mostra os headers — a primeira linha é o status. 200 significa "deu certo, aqui está o corpo".

$ curl -i https://api.exemplo.com/usuarios
HTTP/2 200
content-type: application/json
content-length: 87

[{"id":1,"nome":"Ana"},{"id":2,"nome":"Beto"},{"id":3,"nome":"Carla"}]

Repare no header content-type: application/json: ele avisa que o corpo não é HTML, é JSON — dados estruturados que um programa consegue ler (a aula HTTP explica os métodos e a aula headers detalha cada campo).

Missão: rode curl -i https://api.exemplo.com/usuarios e confirme o 200 na primeira linha, com o JSON dos usuários no corpo.

Passo 3 — provoquer um 404 (recurso que não existe)

Peça um usuário que não existe. Agora o status é 404 Not Found — " pedi, o servidor foi lá, mas não achou". Isso não é erro de rede: a conexão funcionou perfeitamente; o recurso é que não existe (veja a tabela de status).

$ curl -i https://api.exemplo.com/usuarios/999
HTTP/2 404
content-type: application/json

{"erro":"usuário não encontrado"}

Missão: rode curl -i https://api.exemplo.com/usuarios/999 e veja o 404 com a mensagem de erro em JSON.

Passo 4 — enviar dados (POST) e espiar a conversa (-v)

Para criar um usuário, usa-se o método POST com os dados no corpo (-d). Com -v (verbose), o curl mostra a conversa inteira: a conexão TCP, os headers que envia (linhas com >) e os que recebe (linhas com <) — é a ferramenta de debug mais útil de rede:

$ curl -v -X POST -d '{"nome":"Duda"}' https://api.exemplo.com/usuarios
* Trying 93.184.216.35:443...
* Connected to api.exemplo.com (93.184.216.35) port 443
> POST /usuarios HTTP/1.1
> Host: api.exemplo.com
> User-Agent: curl/8.5.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 15
>
< HTTP/2 201
< content-type: application/json
<
{"id":4,"nome":"Duda"}

Tabela — opções de curl para APIs

OpçãoExemploPara que serve
-icurl -i URLMostra os headers da resposta junto com o corpo (o status vem na 1ª linha).
-Icurl -I URLMostra só os headers (faz um HEAD).
-vcurl -v URLModo falante: mostra conexão, DNS, headers enviados/recebidos.
-X METODOcurl -X POST URLEscolhe o método HTTP (GET, POST, PUT, DELETE…).
-d 'dados'curl -X POST -d '{"nome":"Duda"}' URLEnvia um corpo na requisição (com -d, o padrão vira POST).
-H 'Header: valor'curl -H 'Authorization: Bearer …' URLAdiciona um header (ex.: token de autenticação).
Fluxo de bolso para testar qualquer API:
  1. dig api.exemplo.com +short — o nome resolve? qual IP?
  2. ping api.exemplo.com — a máquina responde?
  3. curl -i https://api.exemplo.com/… — o serviço HTTP responde? com qual status?
  4. Deu erro? curl -v mostra exatamente onde a conversa quebrou (a página Problemas comuns ajuda a interpretar).

Resumo do projeto

  • Chamar API = DNS (dig +short) + HTTP (curl); o status (200, 404…) diz o resultado.
  • curl -i mostra headers + corpo; -v mostra a conversa inteira; -X POST -d envia dados.
  • content-type: application/json = a resposta é dados, não página.
