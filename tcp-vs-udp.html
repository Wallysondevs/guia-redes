TCP vs UDP: recibo vs rapidez

Depois que o pacote IP chega ao destino, ainda falta entregar os dados ao programa certo — e fazer isso direito. Essa é a camada de transporte, com dois protocolos rivais. A analogia: TCP é uma ligação telefônica — você confirma que está ouvindo ("alô? tá me ouvindo?"), fala pausado e, se a linha chia, repete o pedaço. UDP é um rádio ou um alto-falante no corredor — você joga a mensagem no ar, rápido, e não sabe se alguém recebeu.

Você vai aprender
  • TCP: com conexão, ordenado, com confirmação (ACK) e retransmissão. Ex.: web (80/443), SSH (22).
  • UDP: sem conexão, sem garantia, leve e rápido. Ex.: DNS (53), DHCP (67/68), vídeo/VoIP, jogos.
  • O que é porta: o par IP:porta (socket) identifica cada conversa.
  • Como ver as portas TCP em escuta com ss -tlnp.

TCP: a ligação telefônica com recibo

O TCP (Transmission Control Protocol) abre uma conexão antes de mandar dados (o handshake da próxima aula), numera cada byte enviado, exige confirmação (ACK) de cada pacote e retransmite o que se perdeu. Os dados chegam na ordem. É mais lento e mais "pesado", mas você tem certeza de que chegou tudo inteiro — ideal para páginas web, e-mail, arquivos.

UDP: o rádio

O UDP (User Datagram Protocol) manda cada mensagem (datagrama) e esquece: sem conexão, sem ordem, sem confirmação, sem retransmissão. É leve e rapidíssimo — ideal quando a velocidade importa mais que a garantia, ou quando o próprio programa cuida da confirmação: DNS (porta 53), DHCP (67/68), vídeo ao vivo e chamadas de voz (pode perder um quadrinho, não pode travar), jogos online, NTP (relógio, porta 123).

Portas: o número da sala dentro do IP

Um computador pode ter várias conversas ao mesmo tempo, então cada uma ganha um número de porta (0–65535). O par IP:porta chama-se socket e identifica a conversa — como o ramal dentro do prédio: o prédio é o IP, a sala é a porta. Portas de 0 a 1023 são as bem-conhecidas (reservadas a serviços padrão: 80 = web, 443 = web segura, 22 = SSH, 53 = DNS).

Na prática, na máquina da Ana

O comando ss -tlnp lista as portas TCP em escuta (esperando conexão) no notebook — repare que é TCP (Netid = TCP):

$ ss -tlnp
Netid State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
TCP   LISTEN 0      128    0.0.0.0:22           0.0.0.0:*     users:(("sshd",1234))
TCP   LISTEN 0      128    0.0.0.0:8000         0.0.0.0:*     users:(("python3",2345))

Já o dig usa UDP porta 53 para perguntar ao DNS — mesmo sem "abrir conexão":

$ dig exemplo.com +short
93.184.216.34

E o curl usa TCP (porta 80 ou 443) para falar HTTP com o servidor:

$ curl -i http://exemplo.com
HTTP/1.1 200 OK
Server: nginx/1.25.3
…

Missão: rode ss -tlnp e veja as portas TCP em LISTEN no notebook da Ana (22 do SSH e 8000 de um servidor local).

Missão: rode dig exemplo.com +short — essa consulta foi feita em UDP porta 53, sem conexão e sem recibo.

Missão: rode curl -i http://exemplo.com — essa conversa foi em TCP porta 80, com conexão, ordem e confirmação.

"UDP não chegou" é difícil de diagnosticar

Como o UDP não confirma nada, se um pacote se perder no caminho ninguém avisa — o programa simplesmente não recebe. Por isso aplicações UDP (vídeo, jogos, DNS) ou toleram perda ou implementam a própria confirmação. Já no TCP, se algo se perde, o remetente retransmite sozinho e você nem percebe.

Resumo

  • TCP = telefonema: conexão, ordem, ACK e retransmissão (web 80/443, SSH 22). UDP = rádio: rápido, sem garantia (DNS 53, DHCP 67/68, vídeo, jogos).
  • Porta = número da conversa dentro do IP; o par IP:porta é o socket.
  • Veja portas TCP em escuta com ss -tlnp (aparece LISTEN).
  • Escolha: precisa de garantia (arquivo, página) → TCP; precisa de velocidade (vídeo, jogo, consulta rápida) → UDP.
