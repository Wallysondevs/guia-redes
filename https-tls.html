HTTPS / TLS — o cadeado da conversa

O HTTP manda tudo em texto puro — como um cartão-postal: qualquer um no caminho pode ler. O HTTPS é a mesma conversa dentro de uma carta lacrada num cofre: só as duas pontas têm a chave. O protocolo que faz o cofre é o TLS, e é por causa dele que o navegador mostra um cadeado.

Você vai aprender
  • A diferença entre HTTP (porta 80) e HTTPS (porta 443).
  • O handshake TLS, resumido: certificado digital, chave pública e a Autoridade Certificadora (CA).
  • O que o cadeado no navegador garante — e o que ele não garante.
  • O header Strict-Transport-Security (HSTS).
  • Comparar as portas 80 e 443 com curl -v no simulador.

O handshake TLS, resumido

Antes de trocar qualquer dado, as duas pontas fazem uma negociação (handshake):

  1. O cliente diz: "olá, suporto TLS 1.3 — estes são os jeitos de criptografar que eu conheço".
  2. O servidor responde com o seu certificado digital: nele há o nome do domínio e a chave pública do servidor, e o certificado é assinado eletronicamente por uma Autoridade Certificadora (CA) — como um cartório que atesta "este domínio é realmente deste servidor".
  3. O cliente confere o certificado: o domínio bate com o pedido? a CA é confiável? o certificado não venceu?
  4. Se estiver tudo certo, o cliente cria uma chave de sessão (um segredo só desta conversa), criptografa ela com a chave pública do servidor e manda.
  5. Pronto: a partir daí, todo o tráfego vai criptografado nessa chave de sessão — só as duas pontas conseguem ler.

Analogia: é como mandar pelo correio um cadeado aberto: só o destinatário tem a chave para fechá-lo. Quem intercepta o cadeado no caminho não consegue abri-lo depois.

No terminal: porta 80 vs porta 443

O curl -v mostra a porta usada na conexão. Compare:

$ curl -v http://exemplo.com
* Trying 93.184.216.34:80...
* Connected to exemplo.com (93.184.216.34) port 80
> GET exemplo.com HTTP/1.1
> Host: exemplo.com
...
$ curl -v https://exemplo.com
* Trying 93.184.216.34:443...
* Connected to exemplo.com (93.184.216.34) port 443
> GET exemplo.com HTTP/1.1
> Host: exemplo.com
...

Mesma página, portas diferentes: 80 para HTTP (texto puro) e 443 para HTTPS (cifrado).

$ curl -i https://exemplo.com
HTTP/2 200
server: nginx/1.25.3
content-type: text/html; charset=UTF-8
strict-transport-security: max-age=31536000

Dois detalhes: o HTTPS moderno fala HTTP/2 (rápido e multiplexado), e o header strict-transport-security (HSTS) manda o navegador só aceitar HTTPS naquele domínio dali em diante — mesmo que alguém digite http://.

Missão: veja o HTTPS conectando na porta 443: curl -v https://exemplo.com — ache port 443

Missão: compare com o HTTP puro, na porta 80: curl -v http://exemplo.com

Missão: ache o header HSTS na resposta HTTPS: curl -i https://exemplo.com

O que o cadeado NÃO esconde: HTTPS criptografa o conteúdo da conversa, mas o nome do domínio ainda aparece na consulta DNS (aula DNS a fundo) — o "endereço do destinatário" continua visível, só a "carta" fica lacrada. E se o certificado estiver vencido, com domínio errado ou de CA desconhecida, o navegador bloqueia com aviso — nunca ignore esse aviso.

Qual porta o HTTPS usa por padrão?

Resumo

  • HTTP = cartão-postal (porta 80, texto puro); HTTPS = carta lacrada (porta 443, criptografada com TLS).
  • No handshake, o servidor mostra o certificado digital (domínio + chave pública, assinado por uma CA); o cliente confere e manda uma chave de sessão criptografada com essa chave pública.
  • Depois do handshake, tudo trafega cifrado — é o cadeado do navegador.
  • curl -v https://… mostra port 443; curl -v http://… mostra port 80.
  • HSTS (strict-transport-security) obriga o navegador a usar só HTTPS naquele domínio.
