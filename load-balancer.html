Load balancer: dividir o tráfego

Um servidor só aguenta tanta gente. Quando um site cresce, a solução não é só comprar um servidor maior — é colocar vários servidores iguais e um atendente na porta que manda cada visitante para o servidor que está mais livre. Esse atendente é o load balancer (balanceador de carga). Analogia: a fila única do banco com vários guichês, e o segurança na entrada distribuindo as senhas.

Você vai aprender
  • Por que um servidor só não escala para sempre;
  • Os algoritmos: round-robin, least connections, IP hash;
  • Balanceamento L4 (transporte: IP+porta) × L7 (aplicação: HTTP, path, host);
  • Health check: tirar servidor doente da fila automaticamente;
  • Sessão persistente (sticky session) — quando precisa.

Como funciona

usuário ──► load balancer (IP público do site, ex.: 93.184.216.34)
                 │ decide para qual servidor mandar
                 ├──► servidor A (10.0.0.11:3000)
                 ├──► servidor B (10.0.0.12:3000)
                 └──► servidor C (10.0.0.13:3000)  « IPs internos, escondidos

O usuário só enxerga o IP do load balancer. Os servidores de trás ficam numa rede interna (o proxy reverso da aula anterior faz esse papel muito bem — nginx, HAProxy, ou LB de nuvem como AWS ALB/ELB, Cloudflare Load Balancer).

AlgoritmoComo escolhe o servidorQuando usar
Round-robinUm para A, próximo para B, próximo para C, recomeça.Servidores iguais, pedidos parecidos.
Least connectionsManda para o servidor com menos conexões abertas agora.Pedidos de duração variada (downloads, APIs pesadas).
IP hashHash do IP do cliente → sempre cai no mesmo servidor.Quando precisa de sessão persistente (sticky).
Least response timeManda para o servidor que está respondendo mais rápido.Ambientes heterogêneos.

L4 × L7: duas camadas de balanceamento

Load balancer L4 (transporte)Load balancer L7 (aplicação)
Olha o quêIP e porta (TCP/UDP) — não abre o conteúdoO pedido HTTP completo: URL, path, host, headers, cookies
VelocidadeMuito rápido, menos processamentoUm pouco mais lento, mais esperto
PodeDividir o tráfego "cegamente"Rotear por caminho: /api → servidores de API, /imagens → servidores de arquivos; fazer TLS, cache, reescrita de URL
ExemplosHAProxy modo TCP, AWS NLBnginx, HAProxy modo HTTP, AWS ALB, Cloudflare

Na prática, quase todo mundo usa L7 com HTTP/HTTPS hoje — dá para fazer muito mais. O L4 ainda faz sentido para protocolos que não são HTTP (bancos de dados, jogos, VoIP).

Health check: o atendente que tira o guichê fechado

O load balancer testa os servidores o tempo todo (ex.: manda um GET /health a cada 5 segundos). Se um servidor não responder (ou responder erro), ele entra na quarentena: não recebe mais tráfego até voltar a passar no teste. Assim, um servidor que caiu não derruba a experiência de ninguém — os outros absorvem a carga. É a mesma ideia do DNS com vários registros (aula de DNS).

Sessão persistente (sticky session)

Se a aplicação guarda estado na memória do servidor (ex.: o "carrinho de compras" fica na RAM do servidor A), mandar o mesmo usuário para o servidor B faz ele "perder" o carrinho. Soluções: cookie que grudada no servidor (sticky), ou — melhor — guardar a sessão num lugar comum (Redis, banco de dados), deixando os servidores stateless (sem estado), que é como se faz hoje em dia.

Missão: rode curl https://api.exemplo.com/usuarios várias vezes. Na vida real, cada pedido pode cair num servidor diferente atrás do load balancer — e todos respondem HTTP/2 200 com o mesmo JSON. rode também curl -i https://api.exemplo.com/usuarios/999 e veja o 404.

Resumo

  • Load balancer = "atendente" que distribui os pedidos entre vários servidores (que ficam escondidos numa rede interna).
  • Algoritmos: round-robin, least connections, IP hash (sticky).
  • L4 vê só IP/porta; L7 lê o HTTP e roteia por path/host — é o mais comum hoje (nginx, HAProxy, ALB).
  • Health check tira automaticamente da fila o servidor que caiu.
  • Prefira servidores stateless + sessão em Redis/banco, em vez de depender de sticky session.
